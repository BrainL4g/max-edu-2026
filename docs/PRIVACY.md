# PRIVACY.md — обработка персональных данных

Документ описывает, какие персональные данные SkillQuest обрабатывает,
зачем, кто имеет к ним доступ, сколько они хранятся и как реализованы
права субъекта. Правовая основа — Федеральный закон от 27.07.2006
№ 152-ФЗ «О персональных данных» (далее — 152-ФЗ).

Машиночитаемая версия того же текста отдаётся публично:
`GET /consent/policy`. Расхождение между этим документом и ответом
эндпоинта — дефект; при изменении правил обновляются оба.

- Версия политики: **1.0**
- Ответственный: оператор SkillQuest
- Контакт по вопросам обработки данных: `privacy@skillquest.example.com`

## 1. Карта данных

| Данные | Где лежат | Зачем | Срок хранения | Кто видит |
|---|---|---|---|---|
| Идентификатор пользователя MAX (`users.max_user_id`) | `users` | связать сессию мессенджера с профилем | до удаления аккаунта | бот (роль `service`), владелец |
| Имя (`users.name`) | `users`, **шифротекст** | обращение в интерфейсе, отчёт по резюме | до удаления аккаунта | владелец, бот |
| Образование и направление (`users.education`, `users.direction`) | `users`, **шифротекст** | подбор вопросов диагностики, миссий, рекомендаций | до удаления аккаунта | владелец, бот |
| Цель и целевая роль (`users.goal`, `users.target_role_id`) | `users` | gap-анализ и подбор миссий | до удаления аккаунта | владелец, бот |
| Результаты диагностики (`user_skills`) | `user_skills` | Skill Map и оценка соответствия роли | до удаления аккаунта | владелец, бот |
| Попытки и XP (`attempts`) | `attempts` | прогресс и выбор следующей миссии | до удаления аккаунта | владелец, бот |
| Текст резюме (`resumes.text`) | `resumes`, **шифротекст** | анализ навыков и пробелов | до удаления аккаунта или по запросу | владелец, бот |
| Имя файла резюме (`resumes.filename`) | `resumes`, **шифротекст** | идентификация загрузки | до удаления аккаунта | владелец, бот |
| Результат анализа резюме (`resume_analysis.result`) | `resume_analysis` | отчёт пользователю | до удаления резюме | владелец, бот |
| Данные о согласии (`consent_given`, `consent_at`, `consent_policy_version`) | `users` | доказательство согласия | до удаления аккаунта | владелец, бот, администратор |
| Хэш токена доступа (`api_tokens.token_hash`) | `api_tokens` | аутентификация | до отзыва токена | никто, хэш необратим |

**Не обрабатываются:** специальные категории персональных данных
(национальность, религиозные взгляды, состояние здоровья, политические
и биометрические данные), данные о несовершеннолетних, сведения об
имуществе.

Резюме — самая чувствительная категория: в свободном тексте пользователь
обычно указывает телефон, e-mail, место работы и проживания. Поэтому
согласие на его обработку запрашивается отдельно и до приёма файла
(см. [раздел 5](#5-согласие)).

## 2. Что зашифровано

Шифрование при хранении — Fernet (AES-128-CBC + HMAC-SHA256), ключ
`DATA_ENCRYPTION_KEY`.

| Таблица | Колонки | Формат в базе |
|---|---|---|
| `users` | `name`, `education`, `direction`, `goal` | `enc:v1:<Fernet>` |
| `resumes` | `text`, `filename` | `enc:v1:<Fernet>` |

Открытыми остаются `id`, `max_user_id`, `target_role_id`, даты и числовые
показатели — по ним нужны индексы, соединения и агрегация.

Значения, записанные до включения шифрования, не имеют префикса `enc:v1:`,
читаются как есть и перешифровываются при следующей записи.

Прочее:

- токены доступа хранятся только как SHA-256 хэш, открытый текст не
  сохраняется и выдаётся один раз при создании;
- сравнение сервисного токена — `hmac.compare_digest`, постоянное время;
- соединение бота с API — внутренняя сеть Docker; наружу API выходит
  только через Caddy с TLS;
- `CORS_ORIGINS` по умолчанию пуст, cross-origin запросы запрещены.

## 3. Кто имеет доступ

| Роль | Токен | Что может |
|---|---|---|
| `student` | выдаётся скриптом, владелец токена = владелец данных | только свои ресурсы; чужой `user_id` → `403` |
| `service` | `SERVICE_API_TOKEN` из окружения, бот MAX | любой пользователь: создание по `max_user_id`, чтение, загрузка резюме, фиксация согласия |
| `admin` | выдаётся скриптом | сброс тестовых данных; полный доступ к ПД админ **не** выдан |

Разделение проверяется на уровне зависимостей (`backend/app/api/deps.py`),
а не в коде роутов: `require_access`, `require_resume_owner`,
`require_attempt_owner`, `require_service`, `require_admin`.

## 4. Передача третьим лицам

**GigaChat (ПАО Сбербанк).** Если в окружении задан
`GIGACHAT_CREDENTIALS` или `GIGACHAT_ACCESS_TOKEN`, текст резюме при
анализе отправляется во внешний сервис искусственного интеллекта.

| | |
|---|---|
| Что передаётся | текст резюме (до 8000 символов), найденные навыки, выбранное направление |
| Куда | `api.giga.chat`; авторизация — `ngw.devices.sberbank.ru` |
| Оператор передачи | ПАО Сбербанк |
| Зачем | оценка готовности резюме 0–100 и краткий вердикт |
| Когда | только при включённом GigaChat и только в момент анализа |

Проверить текущее состояние: `GET /consent/policy` →
`ai_assessment_enabled: true|false`. Флаг истин ровно тогда, когда ключ
GigaChat настроен, поэтому предупреждение в тексте политики можно
проверить, а не принять на веру.

**Других передач нет.** Данные не продаются, не передаются рекламодателям
и страховщикам, не попадают в третьи лица в иных интересах.

**Трансграничная передача не осуществляется** — обработка идёт на
серверах в Российской Федерации.

## 5. Согласие

Правовое основание обработки — согласие субъекта (ст. 9). Оно явное,
фиксируется с датой и версией политики, и может быть отозвано.

```text
📄 Резюме → есть ли согласие?
              ├─ нет  → экран согласия (что / зачем / как / передача в GigaChat / отзыв)
              │           ├─ ✅ Согласен → POST /users/{id}/consent → приём резюме
              │           └─ ❌ Не согласен → резюме не обрабатывается
              └─ да   → приём резюме, кнопка «🚫 Отозвать согласие»
```

Согласие пишется в API **до** приёма резюме. Если запрос не прошёл,
бот не принимает резюме: обработка без зафиксированного согласия
недопустима. Проверка повторяется в обработчиках приёма — без флага
`consent` текст наружу не уходит.

Операции:

| Операция | Назначение |
|---|---|
| `GET /consent/policy` | текст политики, версия, флаг передачи в GigaChat |
| `GET /users/{id}/consent` | текущее состояние согласия |
| `POST /users/{id}/consent` | зафиксировать согласие |
| `DELETE /users/{id}/consent` | отозвать согласие (ст. 9, п. 6) |

Отзыв не удаляет уже собранные данные — это отдельное право, чтобы
отзыв нельзя было спутать с удалением.

## 6. Права субъекта и порядок их реализации

| Право | Статья | Операция | Срок ответа |
|---|---|---|---|
| Получить информацию об обработке | ст. 14 | `GET /consent/policy` | сразу |
| Копия данных | ст. 14 | `GET /users/{id}/data-export` | сразу |
| Уточнение, блокирование, уничтожение | ст. 18 | `PATCH /users/{id}`, `DELETE /users/{id}/data` | сразу / в срок запроса |
| Отзыв согласия | ст. 9, п. 6 | `DELETE /users/{id}/consent` | сразу |
| Обжалование | ст. 17 | Роскомнадзор или суд | по закону |

`GET /users/{id}/data-export` возвращает профиль, идентификатор MAX,
целевую роль и состояние согласия. `DELETE /users/{id}/data` одной
транзакцией удаляет профиль, Skill Map, попытки, резюме с результатами
анализа и токены доступа. Запись в журнале аудита остаётся, но без
связки с удалённым субъектом.

Права доступны владельцу данных и роли `service` (бот). Для чужого
`user_id` — `403`.

## 7. Журнал аудита

Обращения к персональным данным пишутся в лог `skillquest.audit` с
префиксом `AUDIT:`. Состав записи:

```json
{
  "timestamp": "2026-09-29T12:00:00+00:00",
  "action": "read",
  "resource": "user",
  "resource_id": 1,
  "principal_role": "student",
  "principal_user_id": 1,
  "details": {}
}
```

Значения полей в журнал не попадают — только факт, роль и идентификатор.
События формируются на чтении и записи профиля, согласия, резюме,
анализа, диагностики, Skill Map, миссий и рекомендаций, а также при
экспорте и удалении данных.

Полномочия: `admin` и оператор. Роль `student` не читает журнал.

## 8. Действия при утечке

1. **Локализовать.** Прекратить компрометацию: отозвать
   `SERVICE_API_TOKEN`, перевыпустить токены `student`/`admin`, при
   необходимости — сменить `DATA_ENCRYPTION_KEY` с перешифрованием.
2. **Оценить.** Установить состав и категории утечки по журналу
   аудита: `resource`, `principal_role`, временной диапазон.
3. **Уведомить.** Роскомнадзор — в сроки, установленные ст. 19 152-ФЗ;
   затронутых пользователей — по ст. 18.1.
4. **Зафиксировать.** Сохранить выгрузку журнала аудита и результаты
   разбора.
5. **Устранить.** Закрыть вектор, добавить тест на повтор.
